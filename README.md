# PopPin (PP)

공개 웹의 행사 정보와 후기를 찾아 방문 날짜·시간대·여러 장소의 방문 순서를 계산하는 로그인 없는 팝업 플래너입니다.

- Site ID: `appgprj_6ae44de7034c81918eae4eda286b630a`
- 공개 URL: https://poppin-pp.royalbee2048.chatgpt.site
- 실행 환경: Vinext + React + Cloudflare Workers / Sites
- AI: OpenAI Responses `gpt-6.1-sol`, reasoning `low`, 필수 `web_search`, 다른 모델 fallback 없음

## 실행과 검사

Node >=22.13.0 및 lockfile 기준 의존성 설치 후:

```sh
npm run dev
npm test
npx tsc --noEmit
npm run build
```

로컬 개발은 프로세스 환경의 `OPENAI_API_KEY`를 메모리의 개발용 Worker 설정으로 전달합니다. 키를 소스나 .openai/hosting.json에 넣지 마세요. 운영 키는 Sites runtime secret에 설정합니다. `.env.example`에는 키 이름만 있습니다.

## 이름만으로 시작하기

1. 팝업명 두 글자 이상을 입력하고 잠시 멈추면 약 1.2초 뒤 공개 웹 검색을 시작합니다. 한글 조합 중에는 전송하지 않습니다.
2. 방문 기간과 행사 연도, 이름과 주소가 일치하는 후보가 하나면 주소와 장르를 자동으로 채웁니다. 동명·지점 후보가 여러 개면 주소·기간·원문을 보고 직접 선택합니다.
3. 자동입력 값은 수정 가능합니다. 검색에서 확인하지 못한 경우 정확한 이름으로 다시 찾거나 주소와 장르를 직접 입력하세요.
4. 조회가 끝나기 전에 추천 버튼을 눌러도 자동 검색을 먼저 기다립니다. 해결되지 않은 후보 선택이나 빈 주소가 있으면 필요한 행동을 안내하며 빈 값으로 분석하지 않습니다.

이름·날짜 변경과 행 삭제 시 이전 응답을 무시하고 기존 자동 값만 초기화합니다. 조회 도중 직접 수정한 값은 덮어쓰지 않습니다. 서버10분/브라우저5분 캐시와 중복 요청 공유로 같은 검색을 반복하지 않습니다.

## 데이터와 추천 규칙

모든 SNS를 전수 수집하지 않습니다. 요청 시 공개 웹 검색에 잡히는 자료를 분석합니다. 입력한 이름·주소·행사 연도와 실제 일치하는 근거만 행사 판단에 사용합니다. 종료 행사·기간 미확인·장소 불일치·미확보를 구분합니다. 게시일은 확인될 때만 반환하고 조회 시각과 구분합니다. 상세 주소는 그대로 보존하고 검색할 때 도로명·건물번호에서 지역 단위로 넓혀 찾습니다. 넓힌 검색 결과도 원본 주소의 같은 건물·행사·연도 근거가 필요하며, 다른 지점이나 층·호수 충돌은 일치로 보지 않습니다. 원문 URL이 실제 검색 결과에 나타나야 통과하지만, 원문 내용과 사실의 의미 일치는 AI 판단이므로 오류가 있을 수 있습니다.

최대 3곳·14일의 모든 방문 순서를 비교하며, 정확한 시작 시각과 30분 간격 후보를 살핍니다. 현장 입장 가능이 확인된 행사와 예약 날짜·시간을 사용자가 입력한 행사를 일정에 넣습니다. 예약 제공·예약 매진 여부와 현장 입장 가능 여부는 독립적으로 처리합니다. 사전 예약한 장소에서는 날짜·시간을 입력한 뒤 일정 반영 버튼을 눌러 주세요. 예약 필요·매진 행사도 이미 보유한 예약을 입력할 수 있습니다. 입장 정책 미확인은 확정 일정에서 제외하되, 행사·장소·기간·영업시간 검증을 통과하면 조건부 일정으로 별도 계산합니다. 예약은 입력한 날짜·시간으로만 계산하며 행사·주소·방문 기간을 바꾸면 다시 확인해야 합니다. 예약처 조회·인증은 제공하지 않으며 OpenAI 키로 개인 예약을 인증하지 않습니다. 예약 날짜·시간은 외부 AI 검색에 전송하지 않습니다. 입장 마감에는 대기 상한을 포함하고 영업 마감에는 체류까지 포함합니다. 전체 방문이 불가능하면 일부 방문과 제외 사유를 명시합니다.

예약 날짜·시간을 입력하지 않았고 운영 기간과 날짜별 영업시간이 확인된 예약제 행사는 `reservationCandidates`에 예약 확인 후보를 별도로 반환합니다. 방문 조건과 영업시간이 겹치고 희망 체류시간을 넣을 수 있는 범위, 입장 마감, 검증된 예약 안내 출처를 표시합니다. 이는 예약 회차·잔여석·입장 가능 여부나 한산한 시간의 확정값이 아닙니다. 매진·입장 정책 미확인·운영 근거 부족은 예약 확인 후보에서는 제외합니다. 입장 정책 미확인에 대한 조건부 일정은 별도 기능이며, 행사 시작 전 혼잡도 자료 부재는 운영 정보 미확인과 구분합니다.

좌표가 실제 출처에서 확인되어야 여러 장소의 이동을 계산합니다. 좌표가 없으면 단독 일정만 가능합니다. 보행 이동은 직선거리 ×1.3, 시속4km 추정이며 첫 장소까지 이동과 실시간 도로·대중교통은 포함하지 않습니다. 지도 링크로 확인할 수 있습니다.

대기 처리 순서는 같은 날짜 관측 → 과거 관측으로 계산한 추정 → 미확인30분 여유입니다. 고정30분은 예측값이 아닙니다. 같은 방문 수에서는 근거 있는 시간대를 먼저 비교하므로 정보가 비어 있는 시간이 짧은 대기처럼 선택되지 않습니다.

미래 추정은 동일 행사·최근21일·동일 평일/주말·시간대 ±60분에서 2일 이상·3개 이상 관측이 있을 때만 만듭니다. 관측 범위를 보수적으로 확장하며 표본 수, 날짜 수, 최신 시각, 계산 방법과 원문을 표시합니다. 예측 정확도 측정값이 아니며 공휴일·날씨·갑작스러운 현장 변동을 반영하지 않습니다. 표본 부족 시 그래프와 대기 발생시점을 만들지 않습니다.

## 공개 API 비용과 운영 한계

요청8KB·장소3곳·날짜14일·응답6000토큰·검색도구4회·80초 timeout을 적용하며 API 호출은 요청당 최대1회입니다. 키와 upstream 오류 본문을 응답·클라이언트에 노출하지 않습니다. 캐시는10분·최대50건이며 검색근거만 재사용하고 현재시각의 일정과 예측은 매번 다시 계산합니다. 정보 새로 검색 버튼은 기존 캐시를 건너뛰되 요청 제한은 그대로 적용합니다.

자동 검색은 요청4KB·이름2~100자·검색도구2회·출력3000토큰·60초 timeout입니다. 검색과 분석은 같은 비용 한도를 공유합니다. 현재 요청 제한(IP당 총8회/10분 중 검색6회·분석3회, 전체40회/시간, 검색·분석 합산 동시2건)은 **Worker isolate 범위**입니다. 여러 isolate/지역을 합친 전역 비용 상한이 아닙니다. 대규모 트래픽 운영 시 플랫폼 rate binding 또는 Durable Object 같은 공유 제한으로 보강하고 API 계정의 예산·한도를 설정해야 합니다. 사이트는 상시 백그라운드 수집이나 알림을 구현하지 않습니다.

### 행사 후보 검색과 장소 확인

`lib/search-plan.ts`는 원본 입력을 보존하면서 검색용 이름·지역·행사장 힌트를 분리합니다. AI에는 행사명+연도로 후보 발견 → 지역/행사장으로 좁히기 → 원본 주소 교차 확인 순서의 검색 계획을 전달합니다. 상세 도로명·건물번호·층수는 첫 검색의 필수 조건으로 강제하지 않습니다. 검색 계획은 동일한 API 요청·최대 4회 도구 호출 안에서 수행하도록 지시하며, 실제 검색어 선택과 장소의 의미상 일치 판단은 AI가 수행합니다. 별도의 지도 API나 자동 지오코딩을 도입한 것은 아닙니다.

응답에는 후보 행사명·행사장·공개된 주소·장소 확인 상태와 사유를 남깁니다. 확인 출처가 없는 장소 확정, 다른 지점, 여러 후보가 남은 경우는 일정 근거로 사용하지 않습니다. 행사와 기간을 확인했지만 영업시간이 없는 경우에는 행사 정보를 유지하고, 화면에 영업시간 미확인으로 별도 표시합니다. 일부 날짜만 확인되면 확인된 날짜만 계산합니다. 입력창을 수정해도 이미 받은 결과의 상태 표시는 검색 당시 날짜를 기준으로 유지합니다.

`npm test`의 검색·API 테스트는 가짜 응답으로 실행되며 유료 API를 호출하지 않습니다. 상세 주소·지역명·장소명, 지점 불일치·모호한 후보·근거 없는 장소 확정·영업시간 누락을 검증합니다. 이 검증은 파싱과 제외 규칙을 확인하며, 실제 웹 검색 성공률을 측정한 결과는 아닙니다.

API 오류는 크레딧·지출·사용량 한도와 일시적인 요청 속도 제한을 내부적으로 구분합니다. 개발 서버에는 원인을 확인할 수 있는 안내를 반환하고, 운영 서버의 검색·분석 API에는 서비스 이용 불가 또는 요청 집중 안내만 반환합니다. 서버 로그에는 내부 오류 코드와 HTTP 상태만 남기며 API 키·upstream 오류 본문은 기록하거나 반환하지 않습니다.

## 현장 입장과 조건부 일정

- `admission.reservation`은 사전예약 정보, `admission.walkIn`은 현장 입장 가능·불가·미확인과 해당 출처를 나타냅니다. 예약 링크나 예약 매진만으로 현장 입장 불가를 추론하지 않습니다. 현장 입장 주장은 실제 검색의 일치 출처로 별도 검증합니다.
- `plan.days`는 입장 조건을 반영한 기존 일정입니다. `plan.conditionalDays`는 입장 방식이 미확인인 장소를 최소 하나 포함한 별도 대안입니다. 조건부 결과는 확정 결과를 대체하지 않으며 각 장소에 확인할 조건을 표시합니다.
- 조건부 일정도 행사·장소·기간·영업시간·좌표·이동·대기 여유·사용자 예약 시각·입장 마감·체류 제약을 지킵니다. 명시적 현장 입장 불가, 미보유 필수 예약, 매진 좌석을 임의로 허용하지 않습니다. 잘못된 일반 입장 마감 시각이 발견되면 조건부 일정에도 넣지 않습니다.
- `PlanBreakdown`은 실제 선택한 일정에서 방문 수·이동·체류·대기 상한·다음 영업 시작 전 여유를 합산합니다. 미확인 대기 30분은 예측이나 실시간 현장 관측으로 표시하지 않습니다.
- 이 변경은 네이버 지도 직접 조회나 예약처 인증·실시간 대기 API를 추가한 것이 아닙니다. 기존 웹 검색으로 근거를 수집하며 정보 부족과 실제 운영 중단을 구분합니다.

### 개발 QA 화면

기본 행사 카드는 선택한 날짜의 운영시간·입장 마감·도착 안내와 짧은 입장 상태를 표시합니다. 도착 안내는 수집된 문구에 명시된 경우에만 표시하며 알림 발송 기능은 아닙니다. 긴 검증 설명과 검색 출처 탭은 개발 서버에서 `/?qa=1`로 열면 확인할 수 있습니다. API 응답의 출처 데이터는 유지하며, 운영 빌드에서는 이 QA 화면을 켤 수 없습니다.

### 행사 카테고리와 체험 태그

상세 장르 설명은 유지하고, 자동 검색과 행사 조사 응답에 `classification`을 추가합니다. 고정된 대분류·소분류 및 독립적인 체험 방식 태그를 사용하며 근거가 없으면 미분류로 처리합니다. 추가 API 요청 없이 기존 조사에서 분류하고, 취향 점수는 별도로 계산해 일정 순위에 연결합니다. 목록과 검증 방식은 [행사 분류 설계](docs/event-taxonomy.md)를 참고하세요.

### 취향 점수

기존 취향 문장에서 명시적인 분류 선호·비선호를 추출하고, 근거가 확인된 행사 분류와 비교합니다. 대분류 ±30점·소분류 ±50점(주제 중복 가점 없음), 체험 태그당 ±20점이며 행사별 -100~100점으로 제한합니다. 일정 점수와 취향 합계를 분리해 반환하고 합산 순위에 사용합니다. 미분류와 미인식 취향에는 가감하지 않으며 운영·예약 검증은 유지합니다. 반영한 취향과 행사별 점수는 화면에서 확인할 수 있습니다. [취향 점수 설계](docs/taste-scoring.md)에 한계와 검증 범위를 기록했습니다.
